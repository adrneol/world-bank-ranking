**Official Turso read accounting** `[D]`: a "row read" is a *row scan during statement execution*; queries may scan far more rows than they return; aggregate functions (`count`, `max`, …) "result in a row scan for every row considered"; full table scans cost one row scan per row; joins/subqueries cost a row scan for each considered row from all involved tables; unindexed `UPDATE` = full scan + a write per updated row; `select 1` = 1 row read; even aborted transactions incur row writes.

**The architectural fact that governs everything below** `[C][D]`: the backend is a *remote-DB client*. Every SQL statement is a network round trip whose server-side cost is counted in **rows scanned**, not rows returned. The application currently issues several *unindexed, full-table* statements per user request, per status poll, and per boot — this is the 30M-read phenomenon (§16).

## 8. TURSO AS "REMOTE PAGINATED DATA" — correct interpretation (Part 3)

- What persists in Turso: all tables + indexes (server-side B-trees, 4 KiB pages `[D]`), the authoritative committed dataset at all times. Local file in dev is the same schema, same SQL, same driver.
- What lives in Node memory: only the response rows of the current statement, staged ingest rows for the current indicator (O2 caps this at one indicator), progress/retry state, years/integrity memos. **No step loads the database into RAM** `[C]`.
- A SQL result set contains **only the rows the query returns**; the driver never streams the rest.
- But `[D]`: the server scans internally for as many rows as the plan touches — a `COUNT(*)` returns 1 row yet scans 228,776; a `MAX()` returns 1 row yet scans 228,776; a join pays for considered rows on both sides (hence the 457.55K orphan card).
- Indexes reduce *rows touched*: ranking/movement reads are `SEARCH` plans at ~204–816 rows `[P]`; years/fingerprint/orphan checks are unindexed scans at 228,776–578,000.
- Principle to hold: **persistent remote database + targeted SQL + bounded result sets**; never "copy the DB into the process".

## 21. CACHE / METADATA OPTIMIZATION CANDIDATES (Parts 9–11, 26)

- **`dataset_state` (single row)**, written **inside the O7 publish transaction** (and by a one-time bootstrap when absent): `observation_count`, `max_fetched_at`, `max_wb_last_updated`, `years_json` (per-metric year lists + global list), `content_version` (increments only when ≥1 observation row was inserted/updated/deleted), `initialized`. Values derivable exactly:
  - count: delta-maintainable exactly — for each rewritten indicator, `count += stagedRows.length − deletedChanges` (`DELETE` returns changes `[C]`; a post-delete range cannot collide → all batch writes are inserts); unchanged indicators contribute 0. Exactness option B (simpler): one `COUNT(*)` + `MAX(fetched_at)` inside the publish tx per *changed* refresh (≈0.69M, rare).
  - `max_fetched_at`: if any write happened, equals the timestamp written by the last batch (`fetched_at = nowIso()` at build time `[C]`), else unchanged; `max_wb_last_updated`: maintained the same way, or read from the success run when writes occurred.
  - years: computed in-memory from staged eligible rows (exact) or one group-by inside the tx (578K once per changed refresh).
- **Fingerprint response contract unchanged** `[C]` (tests pin `{runId, lastSuccessAt, maxFetchedAt, observationCount}`): same values, read from metadata + fetch_runs instead of scans.
- **Integrity memo**: keep generation-keyed memoization, but key on `content_version` (falls back to current key when metadata absent) so unchanged refreshes no longer force a 1.5M rescan — semantics preserved (integrity inspects only the observations table, which only changes when content_version changes).
- **Years cache**: read `years_json`; invalidate by content_version; recompute only if the row is missing (bootstrap) — removes the 578K per process and per unchanged refresh.
- **Freshness (TTL) stays backend-owned** `[C]` `getCacheStatus` keeps its exact arithmetic (`ageHours < ttlHours`, strict; `[C]` ttlRefresh tests) but sources `observations` from metadata; `lastSuccessAt`/`lastRun` stay on fetch_runs.
- **No time-based caching of TTL decisions**; no analytical-response caching proposed (Part 26): if any later phase adds it, invalidate by `content_version` only.
- **Optional (later)**: per-request middleware memo of the freshness decision for ≤30 s in-process (TTL is 24 h — semantically invisible), invalidated on refresh completion.

## 23. O10 READ OPTIMIZATION CANDIDATES (Part 18)

Current O10 `[C]`: per indicator, one indexed range read of the exact write range, minimal projection (`country_id, year, value, value_raw`), strict element equality including `value_raw`, unknown ⇒ process. Findings:
- The read is **already minimal** for exactness: any coarser check (row counts, `lastupdated`, sampling, checksums over projections) is explicitly rejected by design `[C]` and by Part 18's constraints; a checksum cannot be computed remotely over the staged (in-memory) side without shipping data anyway.
- Cost: 228.78K row reads + ~9 MB egress per full refresh (all 20 indicators) regardless of change; cheap relative to the 30M/month status waste, and it *saves* ~19×220K row writes on unchanged refreshes.
- Possible micro-improvements (defer; only if measurements justify): compare per year (identical semantics, bounded arrays), skip O10 for an indicator whose fetched payload failed (already skipped `[C]`), align the year range exactly with the write range (already exact).
- **Recommendation: no O10 change.** Mark as "not justified".

## 24. TURSO/LOCAL COMPATIBILITY ANALYSIS (Part 15)

Every proposal is plain SQLite SQL executed through the same `driver.js` helpers: a new additive table (`CREATE TABLE IF NOT EXISTS dataset_state` in `schema.sql`), one-row `INSERT … ON CONFLICT DO UPDATE`, and `SELECT`s. Compliance: same SQL semantics (both are libSQL/SQLite 3.5x), same indexes (none added), same repository behavior (single code path), same cache invalidation (content_version), same generation logic (fetch_runs + dataset_state), same refresh semantics (O7/O10 untouched). Local mode stays fully usable without Turso (metadata maintenance runs in the publish tx locally too; tests' temp-file DBs exercise it); production never requires the local DB (fallback untouched; `openExistingLocalDb` still self-heals its own metadata row on first open). Migration: additive only, no column removals; one-time bootstrap when the row is absent (works for both modes); rollback = ignore the table + revert code, values remain valid scans.

## 25. RENDER RESTART OPTIMIZATION (Part 12 / Part 16)

**Target restart:** process start → env checks → Turso client → schema DDL (no-op) → `SELECT 1` → **read `dataset_state` (1 row)** → read `refresh_locks` (1 row, recover stale) → read latest success run (1 row) → `listen()` → (optional, background) integrity only if the content version changed since the last verified run, with its result stored in the memo so the first status reuses it (today's boot call is discarded and duplicated — `[C]` boot integrity result is never placed in `statusCache`).

**Explicit answer (Part 16):** *After a Render restart, the server can safely serve ordinary data after ~5 statements / ~5 row reads:* `SELECT 1`; `SELECT … FROM dataset_state WHERE id=1`; `SELECT … FROM refresh_locks WHERE id=1`; `SELECT * FROM fetch_runs WHERE status='success' ORDER BY id DESC LIMIT 1`; optionally `SELECT MAX(completed_at) FROM fetch_runs WHERE status='success'` (23 rows). **No observation-table statement is required.** Separate phases: *startup validation* = ping + metadata presence (+ one-time bootstrap only if the metadata row is missing: 1 `COUNT(*)` + 2 `MAX()` = ~0.69M, once per database, never per restart); *startup metadata* = the 3 reads above; *first user request* = normal targeted endpoint SQL + cheap freshness check; *later requests* = unchanged targeted SQL. No full observation read, no DB materialization, no local rebuild, no WB download.

## 29. RISKS / ZERO-LOSS (Parts 22, 25, 29)

- **Counter drift** (only real correctness risk) → exact arithmetic in the publish tx + drift detector during explicit integrity + self-heal; failures keep the old scan path.
- **Write economics**: proposals add ≤1 metadata row/refresh and **no** observation writes; O10's write savings are untouched; no index means no write amplification. Rejected: adding indexes solely for MAX (adds one-time 228.78K reads + maintenance).
- **Unchanged-refresh semantics**: switching memo keys to content_version is *more* correct per Part 26; it changes only when integrity/years recompute and (optionally) when the UI refetches — to be decided in 7B-3/7B-6 with tests, never silently.
- **Fallback/degraded modes**: metadata bootstrap must run for the local fallback handle too (it will, via the same publish path; `openExistingLocalDb` bootstraps if absent).
- **No behavior change**: exactly the Part 25 list; no TTL, O1/O2/O7/O8/O10, API, frontend, or data change; nothing may be optimized by weakening integrity or the O8 completeness gate.
