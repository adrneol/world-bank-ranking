ARCHITECTURE & IMPLEMENTATION PROPOSAL — TOTAL GDP ALONGSIDE GDP PER CAPITA
1. EXECUTIVE SUMMARY
Yes — the existing analytical engine can support TOTAL GDP without duplicating any engine, and without changing existing per-capita behaviour.

Evidence from the actual code:

The domain engines are already pure numeric series processors. domain/ranking.js ranks {iso3, value}[] by "value DESC, ISO3 ASC" and explicitly documents "Method (identical for every metric and every year)"; domain/yoy.js computes ((cur/prev)-1)*100 from "RAW World Bank values"; domain/yoyRanking.js, domain/comparison.js, domain/growthComparison.js (like-for-like VALID(A) ∩ VALID(B), entered/exited/outside, decomposition identity) and domain/coverage.js all receive plain observation arrays. None of them reads a metric, a unit, a subject, or a metric-specific rule.
The persistence layer is already indicator-generic: observations(country_id, indicator_id, year, value, value_raw, ...) with PRIMARY KEY (country_id, indicator_id, year). indicators holds code UNIQUE + metric_key UNIQUE. No structural migration is needed to store four more series.
The ingestion pipeline is registry-driven: wb/ingest.js loops metricKeys (default METRIC_KEYS), calls the generic fetchIndicatorSeries(metric.indicatorCode, start, end), applies the one universe rule from domain/universe.js, and isolates per-indicator failures (wb/ingest.js:484-532). Nothing in it is per-capita-specific.
The API layer identifies a metric by req.query.indicator through parseMetric() → getMetric() (server.js:105-115), which is registry-validated and backend-authoritative.
The real obstacles are not mathematical — they are five concrete couplings:

Smallest safe extension: introduce a subject layer above the existing metric registry, keep METRICS/METRIC_KEYS byte-identical (so the per-capita subject is literally the same objects, same keys, same DB rows, same URLs), and give Total GDP namespaced metric keys over the same generic observation store. 4.3 Terminology determination (required by §3 of your brief)
current-price GDP = NY.GDP.MKTP.CD ("GDP (current US$)"). Never call it "real".
constant-price GDP = NY.GDP.MKTP.KD ("GDP (constant 2015 US$)"); in World Bank terminology "real GDP" is a synonym for constant-price GDP — there is no separate "real GDP" indicator. The application should use "constant 2015 US$" in UI text and may map the term "real GDP" only as an explicit gloss.
PPP GDP current = NY.GDP.MKTP.PP.CD; PPP GDP constant = NY.GDP.MKTP.PP.KD (base 2021).
"real GDP at current prices" is a contradiction and exists as no series → NOT AVAILABLE AS A RAW WORLD BANK INDICATOR; must never be produced by deflating/rebasing.
A non-PPP constant series with a base other than 2015 (e.g. "GDP, constant 2021 US$"): NOT AVAILABLE AS A RAW WORLD BANK INDICATOR in the verified candidate set — rebasing KD is forbidden by the app's raw-data rule.
"GDP (constant LCU)" / "GDP (current LCU)" exist but are not cross-country comparable → unusable for a country ranking.
GDP growth (annual %) exists as a raw series, but feeding a percent series into the YoY engine double-applies change; if ever surfaced it must be a distinct, explicitly-scoped decision.
Fabricated-code control test: NY.GDP.TOTAL.CD → [{"message":[{"id":"120","key":"Invalid value","value":"The provided parameter value is not valid"}]}] — the client already parses this error envelope and fails fast (wb/client.js:75-85). This is exactly why codes must be verified, never derived by analogy from PCAP → MKTP.

7. PROPOSED DOMAIN MODEL
Concept: ANALYSIS SUBJECT → METRIC → World Bank indicator → observations. One engine, many subjects.


SUBJECT: gdp_per_capita                    SUBJECT: gdp_total
  metric: nominal_current  ─┐                metric: total_nominal_current   ─┐
  metric: nominal_constant  ├─ same engines  metric: total_nominal_constant   ├─ same engines
  metric: ppp_current       │  same universe metric: total_ppp_current        │  same universe
  metric: ppp_constant     ─┘  same storage  metric: total_ppp_constant      ─┘  same storage
        │                                              │
        └── NY.GDP.PCAP.*                              └── NY.GDP.MKTP.*   (verified codes only)
Rules that make it safe:

The per-capita subject IS the current registry, untouched. METRICS and METRIC_KEYS keep their exact 4 entries and order → identical DB rows, identical DB keys, identical URLs, identical responses, identical tests.
Metric keys are globally unique and namespaced per subject. nominal_current stays per-capita; total GDP uses total_*. This is forced by indicators.metric_key UNIQUE and ingest_year_stats (fetch_run_id, metric_key, year). It also makes ?metric=nominal_current permanently unambiguous (your §11 requirement) with no new required parameter.
A metric declares its subject (metric.subject), so the subject is derivable from any metric key on both sides — no second source of truth, no subject/metric disagreement possible.
Nothing is derived from another series. Each metric carries its own verified indicatorCode; the app never multiplies, divides, deflates or rebases to create a series.
No subject-level math. A subject is only a grouping for navigation and for the multi-metric panels. Ranks/YoY/denominators remain strictly per-metric, exactly as today (PROJECT_REQUIREMENTS.md §3).
Future subjects (inflation, population, trade) need only: (a) a subject entry, (b) verified indicator codes, (c) nothing else. That is the justified-now abstraction. Not justified now: per-subject table schemas, per-subject engines, per-subject endpoints, a subject column in observations, a generic indicator-onboarding framework, or dynamic indicator discovery at runtime (that would break "backend authoritative + curated").
GDP growth (annual %) should remain out of scope now: it is a percentage series whose semantic is already a change, so the level + YoY model must first be explicitly re-scoped for it (documented as future work, §18).

11. INGESTION IMPACT
No second pipeline. The flow for the new series is exactly today's:

Register the four verified codes in config.js (env-overridable, .env.example documented).
Refresh: POST /api/data/refresh (already accepts a narrowed indicators array — useful for a cheap staged first load) or the default/TTL/boot path. 13. DATA-INTEGRITY GUARANTEES
Curated registry only. getMetric() throws on anything unregistered; parseMetric() maps that to 400 INVALID_INDICATOR. No route accepts an arbitrary indicator code into SQL or into the World Bank fetch path.
Verified codes. Registration requires the code to pass /v2/indicator/{code} (documented in .env.example and enforced by a test that pins all 8 codes exactly, mirroring config.test.js:30-41).
No synthetic series. No multiplication/division/deflation/rebasing anywhere; the app's only arithmetic is ranking comparison and percentage change on stored observations. Constant-price series come from the World Bank, never derived (README already states this and must be extended, not weakened).
No cross-subject mixing. Every response names metric {key, subject, indicatorCode, unit}; every panel is scoped to one subject; rankings are computed per metric only.
Fail-closed comparisons. comparisonService already throws COMPARISON_INVARIANT_FAILED rather than returning partial numbers — the new series inherits that.
Integrity checks generalised, not relaxed: H becomes "every configured metric exists in indicators with the exact configured code, and no unexpected code is present" (still catches partial ingests). Checks A–G, I, J stay exactly as they are.
Frontend never authoritative: the subject/metric lists come from the backend (/api/metadata, /api/years), and any unknown key in a URL resolves to the per-capita default exactly as resolveMetricKey does today (App.jsx:137).

FINAL ANSWER TO THE REQUIRED QUESTION
"Can the existing analytical engine support TOTAL GDP by treating it as another economic measure over the same type of country-year observations, while preserving the current GDP-PER-CAPITA system unchanged?"

Yes — with one constraint that is architectural bookkeeping, not mathematics: metric identity must be namespaced per subject, because indicators.metric_key is globally UNIQUE and ingest_year_stats keys on metric_key.

Why it works: every analytical module consumes {iso3, value} / {iso3, year, value} arrays and nothing else (ranking.js header: "Method (identical for every metric and every year)"; yoy.js: "uses RAW World Bank values"). Persistence is a generic (country, indicator, year, value) store. Ingestion is a loop over registry entries calling a generic client. Validation is registry-driven and backend-authoritative. Therefore four additional verified World Bank series (NY.GDP.MKTP.CD, NY.GDP.MKTP.KD, NY.GDP.MKTP.PP.CD, NY.GDP.MKTP.PP.KD) flow through the same pipeline and the same engines and produce valid ranks, YoY, YoY ranks, like-for-like universes, entered/exited/outside sets, coverage and verification — with no engine change and no schema change.

Smallest safe architectural extension (exact list):

config.js: add SUBJECTS (gdp_per_capita, gdp_total), add subject/ppp/baseYear (+ optional display hint) to metrics, add the 4 total_* entries with verified codes; leave the 4 per-capita entries and METRIC_KEYS exactly as they are.
services/integrity.js: generalise check H to the curated registry set.
services/coverageService.js + services/indiaYearly.js + wb/ingest.js: subject-scoped defaults (per-capita default preserved) and a registry-wide ingest list.
server.js: /api/metadata exposes subjects; describeMetric adds subject. No route or parameter changes.
Frontend: subject-aware display registry + one Analysis select in the existing filter bar; iterate the active subject's four metrics instead of METRIC_KEYS; make the handful of per-capita-specific strings subject-aware.
Tests: two deliberate scope-guard generalisations (config "four metrics/forbids MKTP", integrity check H) + the new per-capita freeze/golden regression tests and the Total GDP suites in §16.
Docs: README + PROJECT_REQUIREMENTS.md scope note; .env.example gains the new variables.
Explicitly not implemented (raw-data rule): any derived/synthetic series — rebased constant-price GDP, "real GDP at current prices", GDP assembled from components, deflated series, or any code not verified against /v2/indicator/{code} (control test: NY.GDP.TOTAL.CD returns the World Bank error envelope and must stay unusable). GDP growth (annual %) exists as a raw series but is deliberately out of scope now, because the level+YoY model would double-apply change semantics to a percent series.
